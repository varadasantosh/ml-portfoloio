Inside a PyTorch Inference Image: Wheels, CUDA & Multi-Accelerator Support

When you pip install torch for GPU and then docker build an inference image, you often end up staring at a container that is several gigabytes before a single model weight is added. That size is not an accident — it is the price of the "it just works" experience. This note opens up what is actually inside that image, why a Python wheel can ship an entire CUDA stack, and how one torch package manages to target NVIDIA, AMD, Apple, and Intel accelerators.

This started as a deep dive into Python wheels; here I reframe it around the question an inference engineer actually asks: what is in my serving image, and can I make it smaller?

A wheel is just a ZIP with rules

A wheel (.whl) is a ZIP archive with a fixed layout — you can literally rename it and unzip it:

# A wheel is a renamed ZIP file
cp torch-2.4.0-cp311-cp311-manylinux1_x86_64.whl torch.zip
unzip torch.zip

The filename itself is a compatibility contract:

torch-2.4.0-cp311-cp311-manylinux_x86_64.whl
      │     │     │     │
      │     │     │     └── Platform + architecture (manylinux, x86_64)
      │     │     └──────── ABI tag   (cp311 = CPython 3.11 ABI)
      │     └────────────── Python tag (cp311 = CPython 3.11)
      └──────────────────── Version (2.4.0)

Inside, two things matter for size: the compiled extension modules (.so / .pyd / .dylib — C/C++/CUDA code exposed to Python) and any vendored native libraries bundled alongside them. A *.dist-info/ folder holds the metadata (METADATA, WHEEL, RECORD checksums). Tools like auditwheel (Linux), delocate (macOS), and delvewheel (Windows) are what copy third-party shared libraries into the wheel and rewrite the link paths so the result is self-contained — no system BLAS or CUDA toolkit required at install time. That self-containment is exactly why the files get large.

What's actually inside a PyTorch GPU install

The torch wheel holds the framework: the C++ core (libtorch), the Python bindings, and the dispatcher. On its own that is already in the hundreds of MB. But a CUDA-enabled install pulls in the NVIDIA runtime stack as separate dependency wheels, each one a slice of the CUDA ecosystem:

Package What it is
nvidia-cuda-runtime-cu12 CUDA runtime
nvidia-cuda-nvrtc-cu12 Runtime (JIT) kernel compilation
nvidia-cublas-cu12 Dense linear algebra (the GEMM engine)
nvidia-cudnn-cu12 Deep-learning primitives (conv, attention, norms)
nvidia-cufft-cu12 FFTs
nvidia-curand-cu12 RNG
nvidia-cusolver-cu12 / nvidia-cusparse-cu12 Solvers / sparse ops
nvidia-nccl-cu12 Multi-GPU collectives (All-Reduce, All-Gather)

That is the same cuBLAS doing your matmuls and the same NCCL doing the gradient sync from the distributed-training notes — shipped as pip packages. Added up, a default GPU install commonly lands around 4 GB of dependencies.

There are really three flavors of the install, and the size difference is stark:

  • CPU-only (+cpu): no CUDA at all — on the order of a couple hundred MB.
  • Default PyPI GPU wheel: a slim torch that lists the nvidia-* wheels as dependencies, so pip assembles the CUDA stack from PyPI.
  • Bundled +cuXXX wheel from download.pytorch.org/whl/cu124: CUDA libraries are packed inside the wheel, which is why that single file is well over a GB.

Knowing which one you are pulling is the difference between a lean image and a bloated one.

Why this matters for serving

For an inference image, every one of those gigabytes is cold-start latency, a slower docker pull on every node, a bigger attack surface to patch, and more registry cost. A few levers actually move the needle:

  • Match CUDA to the base image. Installing the default GPU wheel on top of an nvidia/cuda base means you ship CUDA twice — once from the base, once from the nvidia-* wheels. Pick one source of truth.
  • Drop what you don't serve. Pure inference rarely needs NCCL (no multi-GPU collective), and often doesn't need cuDNN if the model is matmul-dominated. Pruning unused nvidia-* libraries can reclaim a lot.
  • Use the CPU wheel where it fits. Small models, embedding services, and pre/post-processing sidecars often don't need CUDA at all.
  • Multi-stage builds. Build/compile in a fat stage, copy only the runtime artifacts into a slim final stage.

The point is that the wheel's self-contained design — great for a laptop — is a cost center in production, and it is controllable once you can see what's inside.

One torch, many accelerators

The second half of the story is portability. The reason model.to(device) reads the same whether device is an NVIDIA GPU, an Apple GPU, or an Intel GPU is PyTorch's device model plus its dispatcher.

  • torch.device("cuda" | "mps" | "xpu" | "cpu") names where tensors live.
  • The dispatcher routes each operator (say, aten::matmul) to a backend-specific kernel based on the tensor's device — cuBLAS/cuDNN on CUDA, Metal Performance Shaders on MPS, oneDNN/oneMKL on XPU and CPU.

Backends fall into two camps:

  • In-tree — shipped with PyTorch: CPU, CUDA (NVIDIA), MPS (Apple Metal), and XPU (Intel GPU, in-tree since 2.4). ROCm (AMD) is interesting: PyTorch's ROCm build reuses the same torch.cuda API via HIP, so most CUDA code runs unchanged — you just install the ROCm wheel.
  • Out-of-tree — plugged in through extensions and "accelerator autoloading," where simply import torch initializes the device module: Google TPU/XLA, Intel Gaudi/HPU, Huawei NPU, and others.

Each target is a separate wheel line — cu124, rocm6.x, xpu, cpu — because each bundles a different native stack. The framework API stays stable; the native libraries underneath are swapped out. The same split shows up in the communication layer: torch.distributed selects NCCL on NVIDIA, RCCL on AMD (NCCL-compatible), oneCCL on Intel, and Gloo on CPU, so the All-Reduce in your training script is backend-agnostic too.

Takeaways

  • A wheel is a self-contained ZIP; for torch that means a bundled (or dependency-pulled) native CUDA stack, which is why GPU images are multi-GB.
  • The heavy pieces — cuBLAS, cuDNN, NCCL — are the same libraries behind the GEMM and distributed-training work elsewhere in this knowledge base.
  • Image size is a deliberate trade-off (portability vs. footprint) and is controllable: match CUDA to the base, prune unused libraries, use CPU wheels where they fit, and build in stages.
  • One stable PyTorch API maps onto many accelerators through the device model and dispatcher; the per-backend wheels are where the hardware-specific code lives.
